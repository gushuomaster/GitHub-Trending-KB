# Obsidian 本地同步反复中断：根因与验证

## 1. 根因类别

- **隐含假设与跨层契约**：安装器假设普通用户能同时注册登录和重复触发器。实测单独的重复触发器可以注册，加入 `AtLogOn` 后返回“拒绝访问”。旧安装器捕获任意异常后静默改用 `HKCU\Run` 启动一个常驻循环，导致用户看到“已安装”，实际却没有能在进程退出后重试的计划任务。
- **数据格式契约冲突**：`.gitattributes` 要求所有 JSONL 行尾为 LF，但 `Index/projects.jsonl` 的已提交 blob 混有 CRLF。2026-10-28 排查时，工作文件与 HEAD 的 SHA-256 完全一致，Git 仍将它报告为已修改，因为属性过滤后的哈希与索引不同。`git restore` 后仍然如此。
- **测试覆盖缺口**：同步脚本在 Windows PowerShell 5.1 下直接调用 `git diff`，把 Git 的正常 stderr 换行警告升级为异常；旧测试没有模拟“Git 退出码为 0、stderr 有警告”的真实组合。

## 2. 以前的修复为何未持续生效

1. 修正代理端口并重启循环，解决了当时的网络连接和进程缺席，但没有检查安装器为何无法建立计划任务。
2. 2026-10-27 09:48 至 14:49，同步确实正常运行；15:19 起触发换行警告并反复失败。旧脚本对该警告的处理没有覆盖到 `git diff` 的直接调用。
3. `loop.log` 最后一次触发是 16:49，之后没有该循环进程。日志没有记录进程退出原因，因此不能断言是谁终止了它；可以确定的是 `HKCU\Run` 无法监督或重新启动已退出的进程。
4. 2026-10-28 本地停在 `dc19be3`，远端已有 `f4843af`。仓库仍指向失效的代理端口 `7900`；当前系统代理是 `7897`，Git 的 Schannel 握手失败，而同端口的 OpenSSL 验证成功。

## 3. 防复发机制

| 优先级 | 机制 | 已采取措施 |
| --- | --- | --- |
| P0 | 运行架构 | 只注册可用的重复计划任务，每次独立执行；注册失败直接报错，不再静默降级到常驻循环。网络失败不会阻止任务安装，下次运行会重试。 |
| P0 | 数据契约 | JSONL 使用 `-text` 保留 blob 原始字节，消除属性转换造成的虚假脏状态。真实本地改动仍受脚本保护。 |
| P0 | 错误判断 | Git stderr 与退出码分开处理；仅把非零退出码视为命令失败，并保留诊断信息。 |
| P1 | 网络恢复 | 配置的代理失败时检测当前系统代理与 Clash 监听端口；当前环境的 TLS 重试使用已验证的 OpenSSL 后端。 |
| P1 | 回归验证 | PowerShell 5.1 测试覆盖混合行尾警告、虚假脏状态与真实内容修改；实际计划任务的自动触发也经过验证。 |

## 4. 系统性扩展

- 其他 Windows PowerShell 5.1 脚本若直接调用原生程序，应分别处理 stderr 和退出码，不能把警告等同失败。
- 安装器必须验证最终使用的调度模式；异常回退若降低可靠性，必须显式告知用户。
- 对“已修好”的判断应包含一次由调度器自动触发的成功执行，而不只是一轮手动同步。

## 5. 知识留存与边界

本仓库没有 `.trellis/spec/`，故把运行契约和排查命令保存在 `Tools/README.md`，并新增 `Tools/tests/obsidian_git_pull.Tests.ps1`。本次已验证本机的定时自动执行；未通过多天运行或重启机器验证。网络服务长期不可用时任务会持续重试并留在 `sync.log`，不会凭空生成缺失日报。
